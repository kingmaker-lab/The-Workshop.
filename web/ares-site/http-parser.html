// 01 — REQUEST DISSECTION

Uma requisição.
Quatro engrenagens.

O módulo recebe fragmentos, reconhece CRLF, valida o cabeçalho e produz uma estrutura C. Ainda não interpreta corpos HTTP ou mensagens subsequentes.

01 / INPUTTCP Bytesfragmentos arbitrários
02 / BOUNDBuffer8192 bytes máximo
03 / DELIMITCRLF CRLFfim dos headers
04 / VALIDATESyntaxmethod · target · Host
05 / OUTPUTRequeststruct ares_request

IMPORTANTE — receber os bytes incrementalmente não significa processar linhas antes de receber CRLF CRLF. Nesta versão, o parsing sintático acontece ao completar o cabeçalho.

// 02 — THE BYTES

O que existe dentro do HTTP?

Nenhuma mágica. Espaços delimitam a request line, CRLF separa as linhas e uma linha vazia encerra a seção de cabeçalhos.

REQUEST / TEXTUAL REPRESENTATIONINPUT
GET /health HTTP/1.1\r\n
Host: localhost\r\n
User-Agent: ARES-Lab\r\n
\r\n

# 0d 0a 0d 0a encerra os cabeçalhos

TARGET: /health
VERSION: HTTP/1.1

// 03 — DEFENSIVE PARSING

Recusar também é engenharia.

Não prometemos interpretar toda a especificação HTTP/1.1. Campos fora do escopo são rejeitados explicitamente para impedir comportamento ambíguo nesta bancada.

01 / VALIDATION⌁

Request line.

Método, alvo em origin-form e versões 1.0 ou 1.1, com separadores estritos e limites de tamanho.

02 / HEADER SAFETY≡

Host e cabeçalhos.

Host obrigatório e único em HTTP/1.1. Nomes token, CRLF e rejeição de bytes de controle e linhas dobradas.

03 / FRAMING!

Sem ambiguidades fingidas.

Corpos, Transfer-Encoding, Expect e pipelining não são suportados. A CLI rejeita bytes após o terminador de cabeçalhos.
