Pela primeira vez, o ARES responde HTTP.

O transporte v0.1 encontra o parser v0.2. Os bytes se tornam uma requisição estruturada, o roteador decide o destino, e o serializador produz uma resposta HTTP/1.1 — com status, cabeçalhos, Content-Length e fechamento explícito da conexão.

// 01 — FROM SOCKET TO RESPONSE

O ciclo agora está completo.

Desta vez há uma aplicação C executável. Ela aceita conexões no loopback, interpreta requisições e envia respostas reais. A Cloudflare hospeda apenas esta documentação.

01 / TCPaccept()127.0.0.1
02 / BYTESrecv()fragmentos TCP
03 / PARSEHTTP v0.2request / headers
04 / ROUTEDispatchmethod + target
05 / RESPONDsend()status + headers + body

ESCOPO — uma requisição por conexão. GET e HEAD. Sem leitura de arquivos, TLS, concorrência ou corpo de requisições. Não é um servidor HTTP pronto para exposição pública.

// 02 — ROUTE TABLE

Uma entrada. Uma decisão.

A v0.3 usa correspondência exata de caminhos. Não interpreta parâmetros enviados por clientes nem reflete conteúdo recebido nas respostas.

GET /200

Project ARES

Uma resposta textual curta com a identidade e os caminhos disponíveis no laboratório.

GET /health{ }

Health Endpoint

JSON estático com status, nome do serviço e versão. Sem dependência de banco de dados.

GET /about200

About

Informações sobre o servidor em C17, as etapas anteriores e o estudo em andamento.

HEAD está disponível para as mesmas rotas e retorna apenas cabeçalhos. Rotas desconhecidas recebem 404; outros métodos, 405 com Allow: GET, HEAD.
